# Write a runner roadmap

Produce controller-defined source roadmaps and, when splitting, an ordered queue plan. Roadmap design does not authorize starting or enqueueing a runner. Workers maintain verified checkbox states in the live roadmap while preserving requirements, and record handoff and evidence in their separate progress file.

1. Resolve repository instructions, destination, scope, existing implementation and deterministic validation commands. Preserve established formats and stable IDs when revising. Done: each requested outcome has observable acceptance; missing authority or facts have an owner and unblock condition.
2. Build the dependency graph and group coherent outcomes into epics. Separate true prerequisites from ordering preferences. Identify independent work beside each external dependency. Done: no cycle, missing dependency or whole-roadmap dependence on an unrelated release gate remains.
3. Divide epics into session-sized tasks, normally 15–45 minutes plus local validation. Keep one roadmap by default; multiple milestones alone do not justify separate files. When a concrete input budget or independent delivery boundary warrants a split, read [roadmap splitting and queues](references/roadmap-splitting.md). Done: each task has bounded context; any proposed queue has an acyclic task graph and file graph, with every file completable using only its own work and validated earlier outputs. Keep coupled work together when a safe split cannot meet these conditions.
4. Read [the task contract](references/task-contract.md) and fill every task field. For a new roadmap, adapt [the template](templates/roadmap.md); for revisions, preserve the controller's established format. Done: every task names deliverable, prerequisites, implementation steps, deterministic validation, evidence and interrupted-work handoff.
5. Apply [the task contract's testing policy](references/task-contract.md#testing-policy): use narrow, bounded checks during functional delivery; put test development, comprehensive test cases and broader validation in a final testing epic after all functionality. For split roadmaps, place that work at the end of the entire sequence, not after each file. Keep implementation independent of final testing tasks unless a concrete technical prerequisite or explicit required gate demands otherwise. Put deployment, production access, manual dogfood and release qualification after the applicable testing gates. Done: functionality can progress with focused evidence while final testing and release requirements remain explicit.
6. Audit all tasks against the contract and dependency graph across every split file. Done: checkboxes follow the contract's standalone task-list syntax, IDs are unique, prerequisites exist, acceptance is observable, required fields are filled, deferred work stays unchecked and every requested outcome maps to work. Check that final testing has one owner per requirement, delivery checks are focused and passing evidence is reused without repeated broad runs. For a queue, apply the reference's preflight to all files together, including acceptance and handoff dependencies; record the checked order and unresolved blockers in the controller index. Report unresolved design judgments to the controller.

Use prepared responses and mocked transports for automated AI validation. Meaningful live-content dogfood requires separate exact scope, a hard request/monetary cap and a stop condition before any provider call. Prepared checks establish mechanics, not model quality or launch qualification.
